Islands and data map

HBX renders as much as possible statically. A component becomes an island only when it needs state or live data that cannot be a link, a form or CSS. Every island ships with static markup that already works, and fails safe: a script error leaves the static page usable.

Data contract

  1. Server prefetch. Page data comes from the template's front matter (the platform's GraphQL data) and is rendered into HTML. Nothing paints from a client request.
  2. One batched client query. All islands on a page register their data needs with a shared client module that merges them into one GraphQL request per tick, dedupes identical fields and caches by key. Targets: at most one request in flight on load, and none when the server already provided the data.
  3. Defer and idle. Islands hydrate on visibility or interaction; only islands needed to use the page hydrate on load.
  4. Fail safe. Each island defines loading, error and empty states, a timeout, and a way back to the static behaviour (form submit, link).
  5. Token handling. The storefront token is passed from the template as a prop (as VariantEnhancer already does); no secrets in the bundle.
